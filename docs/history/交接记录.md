### 2.3 入库过滤

`tagging.worth_remembering()` 是唯一闸门，判据是「这句话在说谁」。

### 4.2 把 `handle()` 里第 4 步换成工具循环

伪代码（照这个结构写，不要自由发挥）：

```
registry = tools.build(cfg, store, ctx, reader, kb)
messages = assembled.messages          # system + 记忆 + 对话，已走过闸门
specs = registry.specs()

for 第 i 轮，最多 cfg["llm.tool_rounds"]（建议 4）轮:
    out = llm.chat(messages, tools=specs)
    if 没有 tool_calls:
        回复 = out.content
        break
    messages.append(out.as_msg_dict())   # 必须带 tool_calls，否则下一轮失忆
    for 每个 call:
        result = registry.call(name, arguments)
        result = 按剩余预算截断（见 4.3）
        messages.append(role=tool, tool_call_id, name, content=result)
else:
    # 轮次用完还没说话：强制收个尾
    追加一条 user「工具用完了，直接回答」
    再调一次，**这次不传 tools**，逼它说人话
```

**两个不能省的细节：**

- `out.as_msg_dict()` 已经写好，会带上 `tool_calls`。漏了这步模型下一轮就不知道自己要求过什么。
- 最后一轮强制收尾时**必须不传 tools**，否则它可能继续调，永远说不完。

### 4.3 工具结果也要过预算

`Registry.call` 单条截到 8000 字符，但多轮累加照样会撑爆上下文。
`gate.py` 只管初始拼装，管不到循环里追加的内容。

建议：循环里维护一个「工具结果累计 token」，超预算就截断当前结果并注明「已截断」。
用现成的 `llm.estimate_tokens()` 估算，配置项建议 `llm.tool_budget`（默认 6000）。

## 5. 设计决策（为什么这么定，别轻易推翻）

- **remember 走语义库，不并存两套记忆。** 模型主动记的和自动入库的落同一个地方，
  走同一套查重和淘汰。这是「融合」而不是「搬运」的关键。
- **知识库单独一份 SQLite，不进记忆库。** 两者读写模型和失败后果不同：
  记忆每条都值钱要能回溯；资料索引坏了重建就行（数据源是 docs/ 目录）。
- **先检索后写入。** 反过来这条消息会把自己捞出来（相似度 1.00），白占名额。
- **一条记忆保留两种说法（主文本 + 别名）。** 换说法更新时，检索和查重都取相似度高的那一边。
- **工具每轮新建 Registry。** 闭包里带本轮会话信息，避免多会话串味。
- **工具失败必须降级成一句说明**，不能让整条回复挂掉。

## 6. 坑（都是实测踩出来的）

1. **批处理必须 GBK + CRLF**，`chcp 65001` 之后不要写中文 echo。
2. **向量模型**要 `HF_HUB_DISABLE_SYMLINKS=1` + `HF_ENDPOINT=https://hf-mirror.com`，
   否则 Windows 上必报 `NO_SUCHFILE`。已在 `app/embed.py` 写死。
3. **`deepseek-v4-flash` 会先思考再答**，`max_tokens` 太小返回空字符串
   （4 个 token 直接空，256 才够）。`llm.py` 会自动放大重试。
4. **模型决定调工具时 `content` 是空的，这是正常的。** 不能当成「空回复」去放大重试，
   否则会把「它想查个天气」误判成失败，白白多打两次请求。`llm.py` 已按此处理。
5. **窗口最小化不影响发送**（UIA 路径能发）。
6. **别用长度猜信息量。**「取更长的那条文本」在两个说法长度相近时直接失效。
7. **「帮我写周报」里的「我」是宾语。** 用「句子里有没有我」判断主语会翻车，
   要先抹掉「帮我/给我/提醒我」这类短语。
8. **`.venv` 在上一级**，批处理里写 `..\.venv\Scripts\python.exe`。
9. `run.py doctor` 重定向到管道时 print 与 logging 会交错（控制台正常），非功能问题。

### 15.1 微信窗口被最小化 → 回复生成了但发不出去（15:45 / 15:47 真实发生）

- 顺序很关键：`_ensure_window()` 必须放在 `_wechat()` **之后**，否则拿到 unknown 等于没检查

### 为什么是「流水」而不是「第二套记忆库」

这是本次最要紧的一条边界。已有的 `MemoryStore` 存的是「关于这个人的事实」——
会查重、会合并、会淘汰、会进上下文。这次新加的是**原话 + 当时判了什么**，

将来群内记忆启用时，记忆条目上记一个 `msg_key` 指回 `data/group_log`，
**不把原话抄一份**。同一条信息存两处，改一边另一边必然走样（§13 踩过）。

### 关键用户怎么认（`app/people.py`）

一条判定链，只看第一条命中的：

1. `data/people.json` 有记录 → 用记录里的 level
2. 没记录但命中 `people.owners` → `owner`
3. 没记录但命中 `group.key_users` → `friend`
4. 都不命中 → `people.default_level`（默认 `stranger`）

只有 `owner` / `friend` 算关键用户；`blocked` 是「完全不处理」，连记录都不留。

- **等级不进 `chats.json`**。那是会话（群/人）维度，一个人出现在十个群里会被复制成
  十份，改一处另九处不知道 —— 和 §12 里「绑定只能有一处」是同一个教训。
- **等级不进记忆库**。它是权限边界：不能被容量淘汰、不能被语义检索捞出来、

- `people.owners` 只是**种子**，不是第二份状态。一旦 `people.json` 给某个 wxid

### 记什么（`app/grouplog.py`）

`data/group_log/YYYY-MM-DD.jsonl`，一天一个文件，一行一个 JSON，两种行用 `op` 区分：

几个细节：

- **回复单独成行，不回写 msg 行**。追加日志的价值就是「永不就地修改」；

## 19. 2026-10-27：修「同一条回复会被发两遍」

**根因不在我们这层，在 wechatauto 内部。** `WeChatGUI.click_send` 判「这条发出去没有」用的是
像素探针 `_input_box_has_text`（数输入框那块区域的深色像素，光标/残留气泡/下方工具栏都会
带偏）；回车其实已经发出去了，探针仍报「还有字」→ `WeChatGUI.send_msg` 外层
`for attempt in range(3)`（`wechatauto/guia.py:2036`，类名是 `WeChatGUI`，不是 `GuiA`）就**重新粘贴同一段文本再回车一次**。我们这层
只看到一次成功的 `send_text`，所以日志里零失败、零重试，微信库里却多一条一模一样的消息。
间隔 6~8 秒（撞上 `rhythm` 拟人节流的 burst 上限时可达 62 秒）就是重发被节流拖出来的。

**修法**（只动 `app/wechat/bridge.py`，另加两处文案）：

- `_install_send_guard()`：给界面通道装一道护栏，只在库自己说「失败」或「又要写一遍」时介入，
  **不改变成功判定的方向**：① 库说「输入框没清空」时用 UIA 读一次真实内容作第二意见
  （发前有字、发后已空 = 确实发出去了，别重发）；② 判断依据是**同一次 `send_text` 调用的
  令牌**（`_call_token()`），不是时间窗。
- 为什么不能用时间窗：`split_reply` 能切出**内容完全相同**的 2~3 个气泡（每段 ≥21 字、换行
  分隔即可），`_send` 在同一线程里隔 1~2 秒依次发；按「N 秒内同文本」拦会把第 2、3 条**静默
  吞掉**（还返回 True，面板全绿）。这一版被 QA 打回来过，别改回去。
- 配置项 `wechat.send_dedupe_seconds`：`0 = 关`；数值只限定台账保留时长，别读成窗口。
- `bot.py:683` 的 `发送完成：N 条气泡 → …` 是这套排查的唯一对照物（我们这层发了几条 vs
  库里真有几条），别删。

**第三层证据：微信库地面真值**（补 R2）。纯 OCR 模式（UIA 读不到输入框）下，前两层都瞎，
所以加第三层：写之前拍 `WeChatGUI._send_watermark(who)`，`click_send` 判失败且 UIA 读不到时回读
微信库，只认「水位之后的新行 + 自己发的 + 正文逐字相等」——所以不会把「上次发过同样的话」
或「别的会话里的同文本」当成这一次；取不到证据一律返回 False，**绝不「宁可少发」**
（判成功会丢掉 `未送达` 留档、并跳过 2s/5s 重试，跟承诺冲突）。实测 OCR-only 一次
`send_text` 的写库条数 4 → 1。四个实现细节，改的时候别踩：

1. `wx.Chat.SendMsg` **不透传** `verify`（`wx.py:575` 只传 msg/target），得直接调
   `_send_watermark` / `_verify_sent`。
2. 水位必须在**首次写动作之前**拍，拍晚了回读永远看不到新行。
3. `who` 必须传会话 id，**不能传 None**（会退化成查自己/当前会话，别处同文本就误判成功）。
4. 回读**自己控时**（`LANDED_TRIES=3` × `LANDED_GAP=0.5s`），别用 `_wait_landed` 那套
   1s×8：它跑在 `Bridge._send_lock`（全局锁，不是按会话）里，一次 `send_text` 最多 4 次
   `click_send`，8s×4=32s 会把**所有会话**的发送一起堵住。读不到就早退，让外层重试来兜。

已知边界：**新会话第一句没有这层保护**——库里一行都没有时 `_send_watermark` 返回 None，
第三层自动跳过（这时若正好碰上 UIA 盲区，仍按库原判）。别为了补这个洞给水位塞一个假
`seq=0`：那会让「显示名解析不到 → 查错会话」重新变成假成功。

### 19.1 主理人拍板的四个取舍（2026-10-27 17:40）

### 24.2 三条必须照做的语义（写在这里防后人「优化」）

1. **`assign` 不就地改 `owner`**。本库是「追加日志 + 快照」，就地改字段等于只改内存 ——
   面板上点一次看着生效，重启之后又变回未归属。正确做法是 `_append("update", new)` →
   `_void(old.id, new.id)` → `_after_write()`，和 `put` 里「换口」同一套。
   测试里有一条**重启回放**断言钉住它（重开一次 `MemoryStore` 看归属还在不在）。
2. **`assign` 不走查重**。`_best_match` 按 owner 分组，而这条记忆在目标 owner 名下本来
   就是「第一次出现」；更糟的是目标名下已有一句很像的话时，查重会把两条合并、把旧条作废
   —— 用户记忆就真少了一条。指派是「换主人」，不是「改口」。
3. **`owner_name` 只在展示层翻译，库里永远只存 id**。名字会变（备注改了、群名改了、
   人退群了），存下来就是第二份状态，迟早和 `people.json` 对不上 —— 这个坑项目吃过一次。

### 24.4 口径说明（我给的规格里有一处自相矛盾，以这里为准）

「只填裸 wxid（不带 `u:`）」**是合法的**，服务端补前缀 —— 面板那个 `prompt` 就是让人手填
wxid 的，要求用户自己加 `u:` 前缀等于让功能废掉。400 只留给真非法值：`""` / `"u:"` /
`"x:xxx"`。另外 `assign` 到 `scope=group` 但没给 `chat_id` 时，会**继承旧记录的 chat_id**
（旧记录是群记忆时）；只有「私聊改成群记忆又给不出群 id」才硬拒 —— 否则会造出
「group 但 chat_id 空」的记录，等于跨群泄漏。

### 25.2 打分模型（顺序即语义，都在 `Engager.judge`）

```
level=blocked → 不回；非群 → 恒回；engage.enabled=false → legacy（hit=None）
否则算六项信号累加：
  at_me +100 / at_unknown +60 / at_other −50 / callname +50 / continuity +40 / question +30 / too_short −30
出 hit：
  被叫到（at_me/at_unknown/callname）→ score >= call_score(50)
  没被叫到 → 仅 owner >= join_owner(45) / friend >= join_friend(60)；stranger 一律不回
```

**关键坑（S1 就埋了、S3 才修）**：`call_score` 只该给「被叫到」用。S1 把它当通用分数线，
导致「陌生人开窗后 40+30=70 ≥ 50」会误回 —— 恰恰违背「陌生人只认 @」。修法是
`if explicitly_called: score>=call_score elif owner/friend: score>=join else False`，
并补了 `演示-接话` 12b + `演示-集成` 陌生人反例两条断言锁死。**谁改判定顺序，先跑这两条。**

### 25.3 三个刻意的取舍（别当 bug）

1. **冷启动不接话**：陌生对话第一句必须被叫到，之后才靠连续性窗口。防插嘴。
2. **连续性信号人人都有，只有 owner/friend 能靠它回**：`TalkState.bonus` 不看等级，
   门槛在 `Engager` 里（stranger join=999）。窗口不落盘（90~180s，重启本身就超过它）。

   发送失败还开窗，会出现「我以为在跟你聊，其实你没收到」。
