# 方案：用户身份识别与记忆隔离

> **状态（2026-10-27 18:40 更新）**：P0 已实现并验收（`交接.md` §22）；
> P1 的「群聊上下文分人 + 单群配额」也已实现（§23）。本文保留为**设计与理由**，
> 代码以磁盘为准；两处偏差点见 §23.3（群聊不给 `remember` 工具）与 §10（per-owner 只做了单群配额）。
>
> **本文只做设计，不含实现。** 所有结论都对着当前磁盘代码（`新版/`，2026-10-27 18:30）核过，
> 引用位置写的是「文件:行」，可逐个复查。
>
> 要解决的问题只有两句你的原话：
> 1. 同一个聊天场景里，它**无法区分不同用户**；
> 2. 切换账号后，它把**所有**人都称呼为同一称谓（「老大」）。

---

## 1. 结论先说

**这不是模型的问题，是数据模型缺了一个维度。**

`Memory` 这个结构里**根本没有「谁的记忆」这个字段**（`app/memory.py:35-53`，14 个字段里没有任何
`owner` / `chat_id` / `user`）。检索也不带身份过滤（`app/retrieve.py:56`，
`search(query, top_k, mark_used)` 三个参数，没有主体）。所以记忆库是一个**所有人都往里写、
所有人都能读到的大锅**。

你库里现在有两条这样的记录（`data/memory/memory.snapshot.json`，都是 `active`）：

```
叫我老大就行
对方让我称呼他"老大"。
```

这两条没有归属，于是**任何**一个私聊进来检索，都可能命中它们 → 模型对谁都喊「老大」。
「切换账号后所有人都是老大」这个现象，到这里就解释完了。

「同一个聊天场景里无法区分不同用户」是另外两个断点叠加：

- 群聊里**完全不读写记忆**（`app/bot.py:502` `hits = [] if is_group else ...`），
  所以群里 A 说过的事，B 说话时它一点都不知道 —— 表现出来就是「记不住具体的人」；
- 会话上下文 `_turns[chat_id]` 里每条消息只有 `{role, content}`（`app/bot.py:515`），
  **没有 sender**，群里三个人的话在模型眼里是同一个「user」在自言自语。

---

## 2. 病因：五个断点（按数据流顺序）

身份信息在系统里其实是**有**的 —— 接入层每个消息都带 `sender`（wxid）和 `sender_name`
（`app/wechat/bridge.py:191-208`）。问题是从「收」到「想」的路上，这个信息被一路丢掉了。

| # | 断点 | 位置 | 后果 |
|---|---|---|---|
| **A** | 身份在编排入口就丢了 | `handle(chat_id, user_text, chat_name)`（`app/bot.py:477`）；调用方 `_flush_body` 有 `msg` 却没传 sender | 从这一行往后，代码再也不知道「谁在说话」 |
| **B** | 记忆没有归属维度 | `Memory` 无 owner 字段（`memory.py:35-53`）；`put()` 不知道写给谁；`search()` 不知道为谁查 | 全局大锅：A 的「叫我老大」会喂给 B |
| **C** | 查重与淘汰也是全局的 | `_best_match` 遍历 `active()` 全体（`memory.py:293-312`）；`_evict` 按全局容量淘汰（`memory.py:319-329`） | 两个人说同一句话会被**合并成一条**（「隔离」在这一层就已经失败了）；话多的人把话少的人的记忆挤掉 |
| **D** | 群聊一刀切不用记忆 + 上下文不分人 | `bot.py:502`；`_turns` 无 sender（`bot.py:515`）；合并窗口按 `chat_id` 合并（`bot.py:332`） | 群内谁都记不住；A、B 两句话 1.2 秒内会被拼成**一条** query，模型看起来像一个人说的 |
| **E** | 「称呼」的来源错了地方 | `people.py` 里的 `alias`（人工设定）**只被群记录模块用过**（`bot.py:436/451/468`，全是 grouplog）；回复链路完全没接 | 该由「人」提供的称呼，退化成了由「全局记忆」提供 —— 于是一次误记污染所有人 |

关于 E 有个细节值得记下来：`people.json` 已经是对的（人维度、有 alias、有等级），
但它在回复链路上根本没被读。也就是说**我们已经有正确的存储，只是没接**。
这条决定了方案的重点是「接线 + 补维度」，不是「新造一套身份系统」。

## 3. 设计目标与非目标

### 目标

1. 任何一条记忆都能回答「这是谁的」；任何一次检索都只返回「这个人的」。
2. 同一个人跨会话可被认出（私聊 / 各个群），但**不同人之间绝不相通**。
3. 群聊里能分清谁在说话（上下文级），并能按人检索（记忆级）。
4. 「称呼」这类身份事实，以人工设定为准，不被模型的一次误记带偏。
5. 迁移不炸老库、不丢结构；旧数据怎么处理要**显式决定**，不能悄悄混进新体系。

### 非目标（本轮明确不做）

- 不做跨设备/多账号合并（一个 wxid 就是一个人，不做「别名合并」）。
- 不做「群公共记忆」的自动抽取（只留结构位，P2 再说）。
- 不改 `chats.json` 的语义（它是**会话**维度：这个群用什么模式、绑什么角色）。
- 不动发送链路、接话判定、群记录（这三块已经有各自的人维度）。

## 4. 隔离模型：三个维度，一条主键

现在系统里混着两套维度，方案要做的是把它们**分开并明确各自职责**：

| 维度 | 键 | 存在哪 | 管什么 |
|---|---|---|---|
| 会话 | `chat_id` | `data/chats.json` | 这个群/这个人用什么模式、绑哪个角色、成员名单 |
| 人 | `wxid` | `data/people.json` | 等级、称呼（alias）、备注 |
| **记忆归属（新增）** | `owner` | `data/memory/*` | 这条事实属于谁 |

`owner` 的取值约定（用一个字段承载两级，避免再加一个字段）：

```
u:<wxid>        某个人的记忆        → "u:wxid_5eg5i11kkyxa22"
g:<chat_id>     某个群的公共记忆    → "g:1234@chatroom"（P2 才写入，先留结构位）
""              未归属（旧数据）    → 永不被任何人检索到
```

配合已有的场景维度（`scope` = `private` / `group`），检索规则只有两条：

| 场景 | 检索条件 |
|---|---|
| 私聊 | `scope == private` **且** `owner == u:当前wxid` |
| 群聊 | `scope == group` **且** `chat_id == 当前群` **且**（`owner == u:当前wxid` **或** `owner == g:当前群`） |

**为什么群聊还要带 `chat_id`**：同一个人在 A 群说的私事，不该在 B 群被捞出来当众复述
（这条隐私红线现在靠「群聊完全不读记忆」实现，代价是全都没得用；带上 `chat_id` 就能
既隔离又不牺牲功能）。

**为什么不按 `chat_id + wxid` 双键做主键**：人和会话是不同维度，双键会让同一个人
的 10 个群变成 10 份互不相通的记忆 —— 那正是「记不住这个人」的另一个版本。

## 5. 身份识别：一条判定链，且身份不能来自记忆

```
sender(wxid, 接入层已提供)
   └─> people.json 有记录？ ──是──> 用它的 level / alias
   └─> 本群成员表 get_group_members(chat_id) 的 nick_name / remark？ ──> 用显示名
   └─> msg["sender_name"]
   └─> 都没有 ──> owner = "u:<wxid>"，显示名用 wxid 尾号（如「wxid…a22」）
```

三条硬规则：

1. **`wxid` 优先于昵称**。昵称会改、会重名；wxid 不变。
2. **owner 的键只能来自 `sender`，绝不能来自记忆或显示名**。否则 B 一进来就继承了 A 的身份 ——
   这是最容易被写错的地方（「查一下有没有叫老大的记忆，有就当他是老大」）。
3. **称呼的权威顺序：`people.alias` > 记忆里的偏好 > 无称呼**。
   人工设定高于模型记的，这条要写进注释，否则下次有人「顺手」改成记忆优先就又回去了。

## 6. 数据模型变更

### 6.1 `Memory` 追加三个字段（都在末尾，旧记录自动取默认值）

```python
owner: str = ""        # u:<wxid> / g:<chat_id> / ""（旧数据，未知归属）
scope: str = "private" # private / group
chat_id: str = ""      # 仅 scope=group 时有意义
```

放在**末尾**是关键：`load()` 里是 `Memory(**item)`，末尾带默认值的字段能让 27 条旧记录
原样载入、不抛异常。这一点已经在上一轮的 `scope` 设计里验证过（同类做法）。

### 6.2 会话上下文 `_turns` 要带人

```python
# 现在（bot.py:515）
{"role": "user", "content": user_text}
# 改成
{"role": "user", "content": user_text, "name": sender_name, "uid": wxid}
```

`Gate.build()` 拼装时：**群聊**给每条 user 消息加前缀「张三：」，**私聊**不加。
模型这才分得清「A 说」和「B 说」。

### 6.3 合并窗口按人拆

`_pending` / `_timers` 的 key 从 `chat_id` 改成 `chat_id|sender`（群聊）。
否则 A、B 在 1.2 秒内各说一句，会被拼成一条 —— 上下文分人在这之前就已经错了。

`_chat_lock` 仍按 `chat_id`（串行边界是会话，不是人，保证同一群的回复不交错）。

## 7. 写入与检索策略（决策表）

| 场景 | 写入 | 检索 | 说明 |
|---|---|---|---|
| 私聊 | ✅ `put(owner=u:xxx, scope=private)` | ✅ 同 owner | 现有行为，只补归属 |
| 群聊 · 关键用户（owner/friend） | ✅ `put(owner=u:xxx, scope=group, chat_id=群)` | ✅ 同群 + 同 owner | P1 开放，配额受限 |
| 群聊 · 陌生人 | ❌ | ✅ 只读同一人的历史？→ **不读** | 陌生人不留痕也不回捞，保持现状 |
| `remember` 工具 | ✅ 带上当轮的 owner/scope/chat_id | — | 模型主动记的条目必须同源，否则又回到大锅 |

**群聊配额**：`memory.group_quota`（默认 80），超出只淘汰 group 里的。
理由和上一轮定的口径一致 —— 不能让群聊把私聊的 400 个名额吃掉。

## 8. 迁移：27 条旧记忆怎么处理

旧记录**没有** owner，事后无法归属（日志里能看出发送者，但记忆条目本身没记）。
当前快照里 **27 条记录、其中只有 3 条 active**（大部分是 10-26 面板调试时手工作废的）。
三种做法，必须显式选一个：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）** | 全部标 `owner=""`，检索永不返回 | 干净、无污染、一条代码都不用改数据 | 等于清空现有记忆 |
| B | 按 `created_at` 去 `bot.log` 反查当时的 `chat_id` 猜 | 能救一部分 | 猜错就继续污染；日志里没 chat_id 的条目救不了；实现成本高 |
| C | 面板加「未归属记忆」列表，人工逐条指派 | 精确 | 27 条要点 27 次 |

建议 **A + C 的组合**：默认全部归档不参与检索，同时在面板给出一个
「未归属记忆（27 条）」列表，想留的（比如「老大」那条如果确实是你的）点一下指派给自己。
这样既不污染，也不粗暴删数据。

> 关键原则：**未归属的数据绝不能默认参与任何人的检索**。宁可「它忘了我」，也不要
> 「它把别人的事当成我的」。

## 10. 容量与淘汰的公平性

现在 `capacity=400` 是全局的，谁话多谁占得多，谁话少谁的记忆先被淘汰。
加了 owner 之后必须一起改，否则「隔离」只是查询层隔离、淘汰层还在互相踩：

```
1) 先按 per_owner_cap（默认 80）在每个 owner 内部淘汰最弱的
2) 再按全局 capacity(400) 兜底淘汰
```

淘汰排序沿用现有口径（`importance` 升序、`last_used_at` 升序），不引入新参数。

## 11. 验证「互不干扰」的测试方式

判据必须是**反例断言**：不只是「A 能查到自己的」，还要「A 查不到 B 的」。
下面每条都能独立成一个断言，建议直接落成 `tests/演示-身份隔离.py`（新增，预计 ≥25 项）。

### 11.1 检索层（最硬的隔离）

| # | 构造 | 断言 |
|---|---|---|
| 1 | A 存「我喜欢美式」、B 存「我讨厌咖啡」，用 A 的 owner 查「咖啡」 | 只返回 A 那条；**B 那条不在结果里** |
| 2 | 故意让 A、B 的两句话**字面完全相同**，相似度 1.00 | 各自只查到自己那条（查重必须按 owner 分组） |
| 3 | A 存「叫我老大」，B 存「叫我小明」，分别查「怎么称呼」 | 互不出现对方的称呼 |
| 4 | 用 `owner=""`（旧数据）去查 | 任何 owner 的检索都返回空 |

### 11.2 端到端（真 `Bot` + 假微信 + 假模型，沿用 `演示-集成.py` 的写法）

| # | 构造 | 断言（抓 `FakeLLM.history` 里的 system 内容） |
|---|---|---|
| 5 | A（wxid_a）发「叫我老大」，再让 B（wxid_b）发「你好」 | B 那次的 system **不含**「老大」，含 B 自己的称呼（或无） |
| 6 | 同一个人隔 1 小时再来（新进程，重开 store） | 仍记得自己的称呼（验证持久化，不是内存态） |
| 7 | A、B 交替各发 3 轮 | 每次 system 的记忆条数 ≤ 自己那几条；交叉污染数 = 0 |

### 11.3 群聊分人

| # | 构造 | 断言 |
|---|---|---|
| 8 | 同群 A、B 在 1.2 秒内各发一句 | 生成**两条**独立 query（不是合并成一条） |
| 9 | 同上后看 `_turns[群]` | 两条消息的 `uid` 不同，且 gate 渲染出的 system 里带「A：」「B：」前缀 |
| 10 | A 在群里说过「我下周三出差」，B 在群里问「你知道我下周去哪吗」 | B 的检索**不返回** A 那条 |
| 11 | A 在 1 群说的事，A 在 2 群被问起 | 按 §4 规则应**不返回**（跨群隔离），这条要显式钉住，免得后人以为是 bug |

### 11.4 迁移与脏数据

| # | 构造 | 断言 |
|---|---|---|
| 12 | 拿现在这份 27 条的真实快照当 fixture | 迁移后全部 `owner=""`，条数不变，且任何检索都查不到 |
| 13 | 旧快照缺 `owner/scope/chat_id` 三个键 | `load()` 不抛异常，字段取默认值 |
| 14 | 手工构造 `scope=group` 但 `chat_id` 为空 | 写入时就拒绝（或读时跳过），不留半截记录 |
| 15 | `owner` 传空 / 传 `u:` / 传非法值 | `put` 直接拒绝并记 warning，不写脏数据 |

### 11.5 容量与淘汰

| # | 构造 | 断言 |
|---|---|---|
| 16 | A 灌 100 条、B 灌 10 条，`per_owner_cap=20` | A 剩 20，**B 的 10 条一条不少** |
| 17 | 全局 400 兜底触发时 | 淘汰来自「条数最多」的 owner，B 仍不受影响 |

### 11.6 回归底线

- 现有 8 个脚本全 `rc=0`（`演示-记忆` 里涉及「同一句合并」的断言需按 owner 重写，
  这属于**语义变更**而非回归失败，要在改动里说明）。
- `pyflakes` / `ruff --select F,B` 干净。
- 真实 `data/` 在测试期间零改动（沿用现有隔离约定：一切写临时目录）。

2. **群聊要不要开记忆**：只对关键用户（我上一份规格的口径）/ 全开 + 配额 / 仍然不开，
   只做「上下文分人」。
3. **同一个人在不同群，记忆是否互通**：按 §4 建议**隔离**（更安全，但会出现
   「他在 1 群告诉过我的事，2 群里想不起来」）。
4. **称呼以谁为准**：`people.alias` 优先（推荐，人工高于模型）/ 记忆优先。
